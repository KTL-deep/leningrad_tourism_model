# E04: контроль рекомендательного сопоставления

## Что измеряется

Версионируемая выборка: `benchmarks/heritage_matching/e04_control_v1.json`. Это **20 специально подобранных пар для разработки**, не случайная и не отложенная выборка: 9 поддерживаются сопоставленными свидетельствами, 7 им противоречат, 4 остаются неопределёнными. Разметка использует исходные записи ЕГРОКН, OSM-теги, адреса, роли и точки. Она не является независимой проверкой физических объектов на местности или юридического статуса.

Включены явные номера, названия/адреса, неразмещённые одноимённые объекты, информационные щиты/остановки, варианты названий и заведомо разные павильоны. Четыре поддержанные пары C15–C18 отсутствовали в выходе v1; это позволяет увидеть пропуски, а не проверять только уже найденные пары. Выборка была подобрана после просмотра v1 и использована для развития последующих версий — оценка на ней **не доказывает обобщающую точность**.

Reviewer-агент размечал пакет без решений алгоритма; основной агент проверил существенные выводы по исходным полям. Две ошибки чтения C15/C16 (перепутанные пары) исправлены **до фиксации меток и расчёта**. Согласованность агентов не заменяет внешнюю контрольную разметку. Исходный локальный пакет: `data/audit/e04_matching_control_20261026T103412Z/blinded-evidence.jsonl`.

## Два разных канала

- `identifier_links` — наличие общей явно указанной строки номера; не принятие пары как единого физического объекта.
- `candidate_retrieval` — объединение ID-связей и кандидатов на проверку. Не означает автоматическое принятие кандидатов.

Для каждого канала отдельно считаются поддержанные, противоречащие и неопределённые выданные пары, а также пропущенные поддержанные пары. Доля поддержанных среди разрешённых выданных пар имеет знаменатель `supported + contradicted`; неопределённые показаны отдельно, **не** считаются верными/неверными. Доля извлечённых среди поддержанных использует только 9 поддержанных контрольных пар. Пустой знаменатель даёт `null`, не ноль и не 100%.

Это условные показатели выбранных пар, **не** точность всей карты, не географическая полнота, не доля найденных всех объектов реестра и не число уникальных заведений. Зависимые пары с одним POI/реестровым объектом не являются независимыми статистическими наблюдениями; популяционные доверительные интервалы по этой выборке не строятся.

## Найденный пропуск `ref:okn`

В сохранённом Павловске 153 POI имеют `ref:okn`. У 152 имеется полная 15-значная строка, совпадающая с номером в подключённом реестре; у одного — 14-значная строка `78161039904044`, которая не дополняется и не исправляется.

[Документация OSM `RU:Key:ref:okn`](https://wiki.openstreetmap.org/wiki/RU:Key:ref:okn) (ссылка страницы на revision 2041648) описывает 16-значный код через Викигид/ВикиВояж. Следовательно, имя тега само по себе не устанавливает пространство национальных 15-значных номеров. Прямая попытка архивировать permanent URL получила HTTP 403; она не обходилась. Утверждения о содержимом основаны на прочитанной публичной странице, а не на вымышленном сохранённом HTTP-снимке.

В v2/v3 применяется только точное равенство полной 15-значной строки существующему номеру реестра. В свидетельстве сохраняются исходный тег/значение, `identifier_namespace_status=ref_okn_exact_registry_value_namespace_unverified` и предупреждение о противоречии длины в документации. 16-значные, 14-значные и иные строки не обрезаются, не дополняются и не превращаются в национальные номера. Несколько номеров и неоднозначные записи не разрешаются выбором первого. Числа из URL КГИОП не используются как номера.

## Воспроизведение оценки v1

Нужен локальный архив снимков из живого пилота, не только JSON с метками:

```powershell
.\.venv-app\Scripts\python.exe -X utf8 -m scripts.validate_heritage_matching `
  --benchmark benchmarks/heritage_matching/e04_control_v1.json `
  --store data/analysis/e03_acceptance_20261024 `
  --matching-snapshot-id aa84ac6e3b06480136ae435e00e48f26db6dbf632e0e9f0c676055a8d9691240 `
  --matching-snapshot-id cfff10efcedfef15f85569f3c1cd4a49af4fb9ec34f023c31544dd9240cf0227 `
  --output data/audit/heritage_control_NEW.json
```

Для нового расчёта нужно новое имя `--output`: существующий файл не перезаписывается. CLI проверяет хэши matching/POI/реестровых снимков, принадлежность области, связь POI с исходным запуском и наличие всех размеченных ID. Даже отсутствующая в выходе пара должна ссылаться на реально существующие записи. Отчёт содержит SHA-256 меток и снимков, версии алгоритмов и протокол отбора. Повреждённые/чужие ссылки, повторные пары, неизвестные метки, нечисловые бесконечности и пустые обоснования отклоняются.

### Исключения слабых кандидатов в v3

Отдельный `excluded_review_candidates` сохраняет пару, свидетельства и причину исключения из очереди кандидатов. Это **не** автоматическая разметка «разные объекты» и не удаление POI:

- Без независимых признаков объекта (`heritage`, `historic`, `building`, `amenity=place_of_worship`) чистые информационные узлы/остановки не становятся объектами наследия только по совпавшему имени. При смешанных тегах такое исключение не применяется. Явная ID-связь сохраняется даже на информационном узле, но получает предупреждение, что ссылка не доказывает физическую идентичность.
- Слабая пара без координат официальной записи исключается, если её номер противоречит другим явно указанным полным номерам POI, для которых **действительно найдены** записи в подключённом реестре. Один неизвестный номер или его повтор у нескольких POI не создаёт такого конфликта. Несколько подтверждённых входных номеров не сводятся к одному.
- Информационные и адресные свидетельства сохраняются в аудите; общий лимит включает исключения. Выходы ID/кандидатов/исключений не пересекаются по паре. Нет словаря «правильных городов», обрезания номеров или полного отбрасывания всех неразмещённых записей.

На контрольной выборке v3 исключил из очереди 4 противоречащие и 2 неопределённые пары. Поддержанные пары не потеряны. Осталась **C09**: неразмещённый «Собственный сад» по адресу Петергофа и одноимённый OSM-сад Гатчины. Адресного геоконтекста для автоматического отклонения таких пар пока нет. Скрывать этот остаточный дефект или считать 9/10 точностью всей системы нельзя.

Все три оценки использовали **неизменный файл меток**, SHA-256 `59e046e02a4dcdb0a53bedc4fb5e52c7ecb0655f8153ed11f3d5b58081a0a092`; правила v3 также разработаны на этих примерах, поэтому это не независимая проверка. Отчёт v3 — `data/audit/e04_matching_control_20261026T103412Z/evaluation-v3.json`. Исключённые пары проверяются на принадлежность исходным снимкам, но не входят в число выданных кандидатов; поддержанная исключённая пара была бы засчитана как пропуск, а не как успех.

Снимки для воспроизведения v3: Павловск `5ac60f33b29079df0e630ff04344768b2da5c220ad508fdfff19c38671e0567f`, Гатчина `0413d87173cf4392c5e0a374ade84fca036e6d84ad84799e72bb56baa97f25ae`. Подставьте их в два параметра `--matching-snapshot-id` команды выше и выберите новое имя выходного файла.

## Адресный контекст населённого пункта — продолжение v4

Оставшийся C09 нельзя исправлять списком «правильных городов» или подменой отсутствующей точки ОКН центром Петергофа. Новый путь использует только явно заданные в адресе компоненты `г.` / `город` и регион исходной записи. Неоднозначные несколько городов, адрес без такого компонента и неподдержанный синтаксис оставляют контекст неизвестным. Исключение для внешнего названия города федерального значения возможно только при точном совпадении с регионом исходной записи, без словаря городов и нечёткого сравнения.

Для слабых неразмещённых кандидатов выполняется ограниченный поиск **населённого пункта**, а не геокодирование объекта: существующий адаптер Nominatim, до 8 уникальных запросов за запуск, проверенный кэш/HTTP-политика/атрибуция. У ответа должны совпасть имя населённого пункта, регион и страна; станция, точка, региональная граница без уровня города или неоднозначный ответ не подходят. Ошибки источника не превращаются в отсутствие объекта и не блокируют независимые ID-связи/ООПТ. Для библиотеки контекст необязателен, для CLI предусмотрено явное отключение.

Габаритный прямоугольник вычисляется из проверенного полигона населённого пункта. Расширение на консервативный запас **5 км** используется только для отбора слабых пар; это инженерное допущение фильтра, **не** рассчитанная транспортная доступность E07 и не обоснованная ошибка источника. Проверяется лишь нахождение явно за расширенной оболочкой. Нахождение внутри неё не доказывает попадание в реальный полигон, а для высоких широт/пересечения линии перемены даты сравнение остаётся неизвестным.

ОКН без координат сохраняет `geometry=null`. Его точка, вход или юридическая граница не создаются. Отдельное исключение пары `unlocated_address_locality_conflict` — лишь отказ от слабого совпадения в очереди, не установление разных физических сущностей. Совпавшие явные номера сохраняются даже при адресном конфликте, с предупреждением.

Первичная проверка доступности Петергофа: `data/audit/e04_locality_probe_20261026T151454Z/report.json`; Nominatim вернул relation/367377, town, регион Санкт-Петербург. SHA исходного ответа `5deacaae747e1ef769e268cd7c157be5063b26a26b847bf170b7a8ded41a7248`. Эта отдельная проверка доступности не является результатом сквозного импорта v4.
