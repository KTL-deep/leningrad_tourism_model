# Измерения OSM: Python, нативный фильтр и Rust-прототип

Статус: первый сравнительный эксперимент завершён **23.10.2026**. Результат обосновывает узкий перенос отбора PBF на Rust, но не полную перепись проекта и не включение прототипа в production без доработок.

## Краткий итог

| Вариант | Wall time | Peak sampled tree RSS |
| --- | --- | --- |
| Исходный Python/libosmium | 702,25 с | 1,44 GiB |
| Нативный tag filter | 169,14 с | 1,44 GiB |
| Tag filter + bbox до геометрии | 134,63 / 142,55 с | 1,44 GiB |
| **Rust-предотбор + общий Python-парсер** | **41,69 / 41,72 с** | **1,10 GiB** |

Все успешные варианты дали **957 POI / 5568 дорог** с одинаковыми нормализованными feature hashes, ссылками узлов, координатами, атрибутами, длинами, статусами unknown и timestamp. Среднее Rust **41,7035 с**: примерно **3,32× быстрее оптимизированного Python-контроля**, **16,84× исходного**, sampled RSS примерно на **23% ниже**. Это измерения данного end-to-end извлечения, не ускорение всего туристического конвейера.

Числа каждого запуска и SHA-256 исходного отчёта: [performance_osm_results.csv](performance_osm_results.csv). Полные отчёты, списки ID/feature hashes, pstats и фазовые артефакты хранятся локально в `data/benchmarks/osm_20261023/`. CSV не выдаёт профилированное время за обычный benchmark.

## Вопрос и границы

Нужно определить, оправдан ли перенос OSM-обработки на Rust **на этом компьютере и этом наборе**, а не обещать ускорение от одного выбора языка. Production-путь остаётся Python + libosmium (C++), геометрия — Shapely/GEOS, геодезические длины — pyproj/PROJ.

Первый объект исследования — `src/etl/osm_extract_parsing.py`, читающий региональный PBF ради одной территории. Скачивание/проблемы Overpass не входят в ускоряемый вычислительный участок. Дальнейшие спрос/маршруты/оптимизация пока не имеют сопоставимого полного рабочего эксперимента; выводы для них не следуют из замера парсера.

## Варианты

1. **baseline** — текущий полный Python/libosmium проход с дисковым sparse location index.
2. **native** — тот же алгоритм и выходы, но libosmium KeyFilter отбрасывает объекты без релевантных ключей до входа в Python. Обработчик координат видит все узлы **до** фильтра; внешние node refs, пересекающие дороги и охватывающие территорию полигоны не теряются. Флаг `native_tag_filter` opt-in, по умолчанию выключен.
3. **native_bbox** — тот же нативный фильтр плюс консервативная проверка bbox координат way до создания Shapely-геометрии. Не использовать правило «есть вершина внутри»: оно теряет пересекающие линии и охватывающие территорию полигоны. Этот контроль отделяет эффект раннего отсева геометрии от выбора Rust.
4. **rust** — экспериментальный Rust-предотбор с ограниченным дисковым индексом, сохраняющий полные координаты потенциально пересекающих bbox ways. Затем общий Python-парсер выполняет точные геометрические проверки/категоризацию/длины. Измерять нужно **весь** Rust → обмен → Python путь, не только быстрый подсчёт объектов. Прототип не является production fallback или новым источником.

Rust-прототип имеет более узкие предпосылки: узлы идут до ways, ID отсортированы, координаты представлены сеткой 1e-7 градуса, индекс не более 2 GiB; отсутствующая ссылка узла у потенциально релевантного way приводит к явной ошибке. Baseline в такой ситуации пропускает way и увеличивает missing_way_locations. Поэтому эквивалентность можно утверждать только для реально проверенного полного входа, не для произвольного частичного PBF; reviewer независимо указал это различие. Автоматически заменять production таким прототипом нельзя.

## Критерии честного сравнения

- Свежий дочерний процесс на запуск; записать версии Python/osmium/Rust, режим release, характеристики машины, хэш исходника и входов.
- Wall time, CPU time и рабочую память различать. Sampled RSS не считать точным пиком; OS peak working set указывать отдельно, если доступен. Учитывать дочерние процессы Rust, не только Python-родителя. Дисковый mmap — не «нулевая память».
- Хэширование большого входа и сборка Rust — отдельные затраты, не скрывать их, но не включать сборку в каждый runtime. Кэш ОС не сбрасывается: такие запуски **не называть cold-cache**. Порядок запусков и число повторов должны быть опубликованы; один замер не даёт надёжного доверительного интервала.
- cProfile использовать отдельным диагностическим запуском либо явно маркировать profiled timings; их нельзя напрямую сравнивать с непрофилированными вариантами.
- Проверять не только counts: уникальные ID, категории/теги, полные node refs/координаты, геометрию, длины, unknown/precision, дату базы. Сравнение нормализованных записей — без зависимости от порядка объектов. Несовпадение делает вывод об эквивалентном ускорении недопустимым.
- Фикстуры обязаны включать пересекающую линию без вершин внутри, замкнутую площадь вокруг территории, отверстия/MultiPolygon, внешние supporting nodes и источник с разреженными глобальными ID. Не применять отсечение ways «есть узел внутри bbox».
- Сбой/таймаут/неполный индекс или неподдерживаемый источник не превращаются в успешный пустой слой. Rust-прототип может иметь более узкие предпосылки — это фиксируется как ограничение.

## Решение по итогам

Переносить компонент на Rust только после совпадения результатов, устойчивого полезного выигрыша времени/памяти и учёта стоимости сборки/сопровождения под Windows. Если простой нативный фильтр даёт сопоставимый результат, предпочесть более простой путь. Кэшировать нормализованный результат по PBF hash + area_id + версии обработки, чтобы повторный анализ не перечитывал весь округ; это отдельный будущий шаг, не измеренный результат этого эксперимента.

Подготовка инструментов: `python -m pip install -r requirements-benchmark.txt` в `.venv-app`. Rust toolchain разворачивается локально, без изменения системного PATH. Первая установка в workspace встретила Windows sharing violation при rename; повтор перенесён в отдельный каталог разрешённого local temp. Блокировка файлов — свойство текущего окружения, не производительность языка.

## Подтверждённые результаты на текущем шаге

- **baseline_01:** wall **702,25 с**, user CPU **646,84 с**, system CPU **67,88 с**. Peak sampled RSS дерева процессов **1543065600 байт (1,44 GiB)**. Счётчики **957 POI / 5568 дорог**, missing_way_locations=0, timestamp совпадает с контрольным источником. Это один прогон без cProfile, не среднее/доверительный интервал.
- В первом отчёте поле `worker_os_peak_wset_bytes` фактически относится к маленькому Windows venv-launcher, **не к основному Python-процессу**. Нельзя использовать его как память парсера. Метрика дерева `peak_sampled_rss_bytes` включает launcher и настоящий worker. Название OS-поля исправлено на `launch_process_os_peak_wset_bytes` для следующих отчётов; исходный отчёт не переписывался.
- Точный код первого измеренного варианта, проверенный по хэшам отчёта, сохранён в `data/benchmarks/osm_20261023/baseline_source/`. Subsequent bbox-контроль добавлен после этого прогона; режимы/исходники в отчётах различимы.
- Rust **release** собран с `--locked` (22,20 с после предварительного скачивания crates). `cargo test --release --locked`: **2 passed**. Фокусные Python-тесты стенда/фильтров/реального бинарника: **18 passed**, без skips, 4,07 с; есть пересечения без внутренних вершин, охватывающие площади, отверстие/MultiPolygon, supporting POI и разреженные ID.
- После baseline была запущена последовательность native (1), native_bbox (2), Rust (2); первая Rust-попытка остановилась на проверке координат. Её исправление и успешный повтор описаны ниже.

### Первый этап сравнения завершён

| Вариант | Непрофилированный wall time | Peak sampled tree RSS | Совпадение с baseline |
| --- | --- | --- | --- |
| baseline | 702,250 с (1 запуск) | 1,437 GiB | контроль |
| native | 169,140 с (1 запуск) | 1,439 GiB | все feature hashes / counts / timestamp совпали |
| native_bbox | 134,625 / 142,547 с (2 запуска) | 1,440 / 1,439 GiB | оба запуска совпали |
| Rust, первая попытка | **неуспех; время не сравнивается** | — | bridge отклонил конфликт координат |

Среднее native_bbox **138,586 с**, предварительно около **5,1× быстрее** исходного контроля. Это ещё не доказанный выигрыш Rust: улучшение получено **без смены языка** и почти без снижения наблюдаемой памяти. Выборка мала, cold-cache/фон ОС не контролировались; нельзя приписывать весь эффект только одной операции или публиковать доверительный интервал по этим запускам. Исходники native-замеров сохранены в `native_source_01/` с повторной проверкой соответствия хэшам отчёта.

### Выявленные и исправленные расхождения

Первый Rust scan завершился, но Python bridge отверг `conflicting shared node coordinates`. Проверено, что `osmpbfreader::Node.lon/lat` вычисляют `integer * 1e-7`, а mmap lookup использовал `integer / 1e7`: например, 300000001 даёт два соседних f64. Исправление сохраняет исходные `decimicro_lon/lat` непосредственно в индексе и применяет единое преобразование. Bridge канонизирует координаты на заявленной сетке 1e-7, а не ослабляет сравнение произвольным допуском. Разные узлы/разные точки сетки по-прежнему должны конфликтовать.

Отдельная фикстура неполного PBF выявила прежний дефект baseline: lon/lat читались **до** проверки valid(), а `osmium.InvalidLocationError` не входит в ValueError/RuntimeError. Проверка перенесена до чтения координат. Теперь baseline действительно учитывает missing_way_locations, а Rust остаётся явно более строгим и отвергает неполный источник. На реальном измеренном источнике missing=0; геометрические результаты исправление не должно менять, это проверяется повторным сравнением.

После исправлений release пересобран, фокусные тесты с настоящим бинарником: **20 passed**, 3,21 с. Reviewer повторно проверил изменения без тяжёлого запуска, конкретных оставшихся дефектов не указал. Затем выполнены **Rust 2 запуска → отдельный cProfile native_bbox**. Профилированное время не включается в таблицу обычных скоростей. Подтверждённые результаты приведены далее.

## Финальные измерения и профиль

Серия после исправления успешно завершена: `rust_02.json` содержит **41,688 / 41,719 с**, оба запуска эквивалентны первому baseline и друг другу. Tree sampled RSS **1185439744 / 1184313344 байта**. CPU Python-родителя не включает всю работу внешнего Rust: для приблизительного CPU всего дерева использовать поля tree_sampled_cpu, а не Windows os.times.children (на этой платформе недоступно). Общий sampled user+system CPU дерева около **57,84 / 58,27 с**; это нижняя оценка по последнему наблюдению каждого процесса, не точный cross-process peak/counter.

Фазы из `rust_stages.json` обоих запусков:

| Фаза | Запуск 1 | Запуск 2 |
| --- | --- | --- |
| Rust-процесс: полный scan, индекс, кандидаты | 37,016 с | 37,344 с |
| Валидация кандидатов Python bridge | 0,359 с | 0,359 с |
| Заголовок + запись малого PBF | 0,485 с | 0,578 с |
| Общий Python-парсер малого PBF | 3,140 с | 2,781 с |

Прочитаны **89029204 узла и 7311518 ways**; выданы **10041 кандидат**, в том числе **7255 ways**, восстановлены **32672 supporting nodes**. Candidate NDJSON **2917049 байт**, малый PBF **399886 байт**. Индекс 16 байт на исходный узел — примерно **1,33 GiB временного диска**, это не бесплатная память и не готовый постоянный кэш. Общий wall time включает запуск процессов/передачу/запись/повторный разбор/очистку; фазовые времена не скрывают bridge.

Отдельный диагностический `native_bbox_profile_01.json` завершён за **242,64 с**, результат также совпал; это время **не сравнивать** с unprofiled 134–143 с. cProfile: **222576091 вызов**, около **1499828 вызовов way()**, **25402560 обращений к node refs**; обработчик way имеет около **199,4 с cumulative** из примерно 240 с парсинга. Время вложенных функций перекрывается, складывать cumulative нельзя. Существенные участки — Python-доступ к refs/валидности/координатам и обход тегов, а не только запись JSON. Это поддерживает перенос чтения/индексирования/раннего отбора до перехода в Python. cProfile не раскрывает внутренние фазы нативного libosmium и не является отдельным сравнением скорости C++ и Rust.

## Что переносить и что оставить

| Компонент | Решение по этому эксперименту | Основание |
| --- | --- | --- |
| PBF scan, дисковый индекс координат, ранний отбор nodes/ways | **Кандидат на production-перенос в Rust** | Полный Rust+Python путь около 41,7 с против 138,6 с оптимизированного контроля, результат совпал |
| Повторное использование уже отобранного набора | **Сначала добавить кэш по input SHA + area_id + версии алгоритма** | Нельзя перечитывать 89 млн узлов ради неизменившегося результата; эффект кэша этим экспериментом не измерялся |
| Точная геометрия, категории, геодезические длины | **Пока оставить общий Python/Shapely/pyproj** | После отбора Python-часть занимает около 3 с; она уже использует нативные GEOS/PROJ. Полная перепись имеет небольшой предельный выигрыш и риск иной семантики |
| HTTP-адаптеры, политика источников, снимки/манифесты | **Оставить Python** | Нет измеренного CPU-бутылочного горлышка; Rust не исправляет недоступный сервер |
| Streamlit, отчёты и методика/правовые правила | **Оставить Python** | Не являются предметом полученного ускорения, важнее прозрачность и тестируемость |
| Спрос, маршруты, оптимизация сочетаний | **Решать после реализации и отдельного профиля** | Этот эксперимент не даёт измерений полного нового расчётного конвейера |

### Порядок следующего production-среза (ещё не реализован)

1. Зафиксировать версионируемый контракт native-отбора и целочисленных координат, сохранить source timestamp/хэши/полноту и согласовать поведение на missing refs, unsorted PBF и разных гранулярностях. Добавить реальные контрольные наборы вне Гатчины.
2. Подключить Rust как **явно выбираемый** backend к общим SourceSnapshot/RunManifest; отсутствие бинарника или неподдерживаемый формат должны давать понятную причину, повреждение источника не маскировать успешным fallback. Рабочий default пока не переключать.
3. Добавить проверяемый кэш результата и тесты invalidation/повреждений/повторного запуска. Сохранить полный node refs, запрет ложных маршрутов и partial для relations.
4. Выпускать проверяемые release-артефакты под поддерживаемые ОС, чтобы обычному пользователю не требовался Rust-компилятор. `target/` не коммитить, toolchain/сборка — операторский этап. Затем повторить сравнение на нескольких территориях/размерах и отдельно холодном/тёплом кэше.

**Не сделано намеренно:** автоматическое переключение production CLI на Rust, PyO3-интеграция, полный Rust GIS/оптимизатор, обещание маршрутов/эффектов или масштабирования на всю область. Текущий результат — проверенный эксперимент и обоснование границы переноса.

## Итоговые проверки и ограничения

Полный `.venv-app` pytest с `OSM_RUST_PRESELECT`, указывающим на настоящий release binary: **481 passed, 3 xfailed**, 20,29 с, без skips. `cargo test --release --locked`: **2 passed**. `pip check`: No broken requirements found. `git diff --check`: OK (только предупреждения LF → CRLF). Текущие измеренные Rust binary/bridge/common source повторно сверены с SHA-256 отчёта.
