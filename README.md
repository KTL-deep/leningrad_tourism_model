**Цель проекта** — система поддержки решений администрации по развитию туристического каркаса Ленинградской области. Пилот: **Павловск (Санкт-Петербург) — Гатчина (Ленобласть)**. Результат новой модели — сочетания мероприятий с обоснованием, а не обязательная смена типа застройки каждого блока.

Проект находится в поэтапной пересборке. Актуальная методика: [мастер-план v1.1](TOURISM_FRAMEWORK_CODEX_MASTER_PLAN.md); фактическая готовность: [журнал](docs/implementation_status.md). Сохранённая AHP/SA-модель — исследовательский baseline, не подтверждённый прогноз. Описанный ниже старый конвейер не означает готовность новой системы.

## Принятая политика данных — 19.10.2026

- Единственный обязательный пользовательский ввод — территория. Сбор строится на сменных поддерживаемых источниках по общей схеме, не на одном документе для города.
- Официальную статистику программа ищет, получает и проверяет автоматически. Если подходящего набора нет, он **исключается из численных входов с причиной**; пользователь не готовит PDF/таблицы, независимый анализ продолжается. Неизвестное не заменяется нулём.
- Пространственная база: объекты, связи и доступность. Отзывы/оценки — дополнительный слой сообщений о проблемах и активности только при разрешённом доступе. Число отзывов не равно посещаемости, жалоба не является измеренной нехваткой мощности.
- PDF допустим как необязательное обогащение/контрольный пример. Яндекс, платная лицензия, личный кабинет и LLM не обязательны. Документированный API поиска организаций Яндекса не подтверждает доступ к текстам отзывов.
- Если входов для D/K недостаточно, соответствующий количественный дефицит не вычисляется как факт. Ограниченный результат явно отделяется от условных сценариев.
- Отсутствие официальной статистики не отменяет правовых проверок. Неизвестная допустимость не означает разрешение строительства.

**Что реально есть сейчас:** baseline, офлайн-тесты, CLI разведки и необязательный PDF-адаптер; контракты/хранилище E02, StudyArea и политика допуска. Сбор границ проверен на реальных ответах Гатчины/Павловска. Overpass CLI сохраняет причины отказов API, не ложные нули. Отдельный резерв `scripts.collect_osm_extract` проверен на реальном PBF Geofabrik: **957 POI и 5568 дорожных линий Гатчины**. Резерв остаётся partial: relations не поддерживаются. Решение по интеграции PBF в общие манифесты — [ADR 0010](docs/decisions/0010-streaming-pbf-provenance.md), фактический результат проверок — в журнале. Это **не** готовые маршруты, туристические эффекты или разрешения мероприятий. Окружение, режимы/расписания, поиск статистики, отзывы и полный пользовательский путь ещё не готовы. Навигация — [docs/README.md](docs/README.md).

## Первый пространственный шаг новой реализации

```powershell
.\.venv\Scripts\python.exe -X utf8 -m scripts.collect_boundary "Гатчина, Ленинградская область, Россия"
.\.venv\Scripts\python.exe -X utf8 -m scripts.collect_boundary "Гатчина, Ленинградская область, Россия" --offline
```

Команда предназначена только для **одного явно выбранного пользователем региона/населённого пункта**. Она получает полигон через поддерживаемый Nominatim, проверяет геометрию/CRS, сохраняет исходный ответ и манифест в локальное `data/analysis/`. Повтор использует проверенный кэш; `--offline` запрещает сеть и завершается ошибкой при отсутствующем/просроченном кэше. Возвращаемый статус partial — только граница: POI, сеть, окружение, статистика и отзывы этой командой ещё не собираются; туристических рекомендаций нет. Несколько возможных полигонов требуют уточнения территории, станция вместо города не выбирается.

Использование публичного сервера ограничено [политикой Nominatim](https://operations.osmfoundation.org/policies/nominatim/): идентификация приложения, кэш, не более одного запроса в секунду суммарно. CLI применяет интервал 1,1 с и общую блокировку внутри каталога кэша. Не запускать несколько копий с разными хранилищами, не использовать как адресный generic-сервис, autocomplete, массовый сбор POI или периодический геокодер. Для иных нагрузок нужен отдельный согласованный источник/развёртывание. При оставшейся после аварии блокировке программа не удаляет чужой lock автоматически.

Расширенная операторская настройка `NOMINATIM_ENDPOINT` позволяет сменить HTTPS `/search` endpoint без правки кода; нестандартный endpoint допускается только при явном `NOMINATIM_TERMS_CONFIRMED=1` после проверки условий и прав оператором. Учётная запись/ключ или платный поставщик для стандартного запуска не требуются. Атрибуция — `© OpenStreetMap contributors (ODbL)`. OSM-геометрия и источник юрисдикции не являются юридическим заключением; расчётное окружение и метрическая CRS автоматически не выдумываются.

## OSM-наблюдения POI и дорожных линий — E03 partial

```powershell
.\.venv\Scripts\python.exe -X utf8 -m scripts.collect_osm "Гатчина, Ленинградская область, Россия"
.\.venv\Scripts\python.exe -X utf8 -m scripts.collect_osm "Гатчина, Ленинградская область, Россия" --offline
```

При успешном источнике сохраняются исходный ответ, манифест и независимые GeoJSON-копии в `data/analysis/exports/` (пути/хэши в JSON-ответе). Проверяются timestamp базы, финальный счётчик и ссылки узлов; remark/обрыв не считаются пустой успешной загрузкой. Все части MultiPolygon входят в явный bbox. Центры ways/relations помечены приблизительными, неизвестные мощности не заменяются 0. `routing_ready=false`: это ещё не сеть с проверенными режимами/окружением и не расчёт времени маршрутов.

Default Overpass: [Private.coffee, условия](https://overpass.private.coffee/); обязательна атрибуция OSM/ODbL, TLS и умеренная нагрузка. Технические лимиты: 1000 км² bbox, 16 MiB/200000 элементов; автоматических переборов зеркал/крупных территорий нет. Оператор может задать `OVERPASS_ENDPOINT` (HTTPS `/api/interpreter`) и `OVERPASS_TERMS_CONFIRMED=1` после проверки условий. Только ограниченный повтор временных 502/503/504/timeout, без обхода 403/429.

**Фактический live-результат 19.10.2026:** Private.coffee вернул 500, основной сервер 502, VK 504. Новый CLI сохранил границу Гатчины, error и исключения POI/network; счётчиков/слоёв реальных объектов нет. Offline с отсутствующим валидным кэшем также даст явную ошибку, не синтетические данные. Экспорт/полнота/кэш на положительном ответе подтверждены пока только офлайн-фикстурами. Детали — [ADR 0007](docs/decisions/0007-counted-osm-inventory.md), [validation](docs/validation.md).

### Резервный региональный PBF — отдельный частичный срез

```powershell
.\.venv\Scripts\python.exe -X utf8 -m scripts.collect_osm_extract "Гатчина, Ленинградская область, Россия"
.\.venv\Scripts\python.exe -X utf8 -m scripts.collect_osm_extract "Гатчина, Ленинградская область, Россия" --offline
```

Команда автоматически проверяет покрытие территории полигоном выгрузки Geofabrik Северо-Запада и загружает **около 625 МБ** PBF (лимит 768 MiB) в локальный кэш. Требуется `osmium`, включённый в audit lock. TLS, размер/длина/хэш, ограниченный переход с latest на датированный файл и срок кэша проверяются. За пределами поддерживаемого региона или при отсутствии пригодного offline-кэша — явная ошибка, не другой источник без уведомления. Это не автоматическое переключение старого CLI.

GeoJSON содержит только node/way-наблюдения POI и исходные дорожные линии; relations пока не обрабатываются, результат **partial**. Центры ways приблизительны, неизвестная мощность остаётся неизвестной, `routing_ready=false`. PBF потоково копируется в независимый архивный `SourceSnapshot`; граница, исходные байты и снимки экспортов связаны общим `RunManifest`. Это требует ещё около 625 МиБ для архивной копии и не означает приёмку полного E02/E03. Неполные наблюдения сохраняются как supporting-артефакты: сбор имеет статус `partial`, оценка готовности входов — `failed`, пока POI/сеть не отвечают контракту. Это не ошибка архивации и не готовая карта рекомендаций. Идентификатор запуска выводится CLI; в идемпотентных GeoJSON он остаётся null, связь задаётся манифестом. Проверки — в [validation](docs/validation.md), решения — [ADR 0008](docs/decisions/0008-geofabrik-extract-fallback.md) и [ADR 0010](docs/decisions/0010-streaming-pbf-provenance.md).

**Реальная проверка 23.10.2026:** PBF загружен и проверен по длине/хэшу; исправленный offline-разбор Гатчины дал **957 POI и 5568 дорожных линий** (база OSM 21.10.2026). Оба GeoJSON отдельно проверены по хэшам/геометрии/ID/ссылкам узлов. Полнота реальных услуг и туристические эффекты этим не подтверждены.

Сравнительный эксперимент [performance_osm.md](docs/performance_osm.md) завершён: на этом PBF/Гатчине baseline **702 с**, Python с нативным фильтром и bbox **135–143 с**, Rust-предотбор + общий Python-парсер **41,7 с**; полное совпадение объектов проверено. Это обоснование узкого переноса PBF-отбора, не ускорение всего приложения. Прототип изолирован в `benchmarks/`, production-default не переключён; ограничения и следующий план интеграции опубликованы вместе с замерами.

## Историческое описание baseline: архитектура и конвейер

Ниже сохранено описание старой концепции для ориентира по коду. Его формулы и заявления о прогнозе/оптимальности не считаются проверенными. При расхождениях действует мастер-план v1.1, а не этот исторический раздел.

Вычислительное ядро построено на базе библиотеки пространственного анализа [BlocksNet](https://github.com/iduprojects/blocksnet). Весь конвейер (Pipeline) автоматизирован и состоит из 5 основных шагов:

### 1. Топологическая генерация (Пространственная дискретизация)
Пространство (на основе данных OpenStreetMap) алгоритмически "нарезается" на компактные городские блоки (UCM — Urban Context Models). Границами блоков выступают строгие физические барьеры среды: автомобильные дороги, железнодорожные магистрали и реки.

### 2. Семантическая экстракция (UCM Builder)
Каждый сгенерированный топологический блок обогащается семантикой. Алгоритм проводит пространственное соединение (Spatial Join) с различными слоями ГИС-данных:
* Объекты Культурного Наследия (ОКН)
* Особо Охраняемые Природные Территории (ООПТ)
* Лесные и парковые массивы
* Объекты туризма, питания и социальной инфраструктуры (OSM POI)

Также на этом этапе с использованием графов (NetworkX) строится **матрица транспортной доступности** между всеми блоками.

### 3. Сценарное взвешивание (AHP + WLC)
Метод анализа иерархий Томаса Саати (AHP) в связке с Weighted Linear Combination (WLC) используется для расчета агрегированных индексов пригодности ($S_{ik}$) каждого блока под конкретные функции:
* 🌲 Парк / Рекреация
* 🏠 Жилая застройка
* 🏪 Коммерция / Услуги
* 🚉 Инфраструктурный Хаб

Расчет производится **мультисценарно**: веса пересчитываются для сценариев *«Экоцентризм»*, *«Историко-центризм»* и *«Инфраструктурный»*.

### 4. Эвристическая оптимизация baseline (Simulated Annealing)
Алгоритм имитации отжига назначает блоку категорию (`Target Land Use`) в рамках старой целевой функции. Глобальная оптимальность не доказана.
Целевая функция максимизирует индекс пригодности ($S_{ik}$) и одновременно учитывает **пространственную синергию** (например, жилую застройку алгоритм старается размещать ближе к паркам и инфраструктурным хабам). 
Также рассчитывается условный `Capacity`, зависящий от пригодности; он не является проверенной физической мощностью или экологическим пределом.

### 5. Интерактивный UI Дашборд
Слой `Streamlit` + `Folium` предоставляет интуитивно понятный картографический веб-интерфейс для стейкхолдеров. Пользователь может на лету переключать сценарии развития, визуально оценивать предписанную модель землепользования и изучать аналитику по каждому блоку во всплывающих окнах.

## Установка и запуск старого baseline (полный путь пока не проверен)

### 1. Установка окружения
Рекомендуется использовать виртуальное окружение.
```bash
git clone <repository_url>
cd leningrad_tourism_model
python -m venv .venv
# Активация окружения (Windows):
.venv\Scripts\activate
# Активация окружения (Linux/Mac):
# source .venv/bin/activate

# Полный стек отдельно от минимального audit-окружения (.venv):
# нужен Git для закреплённой upstream-версии BlocksNet
python -m venv .venv-app
.\.venv-app\Scripts\python.exe -m pip install -r requirements.txt
.\.venv-app\Scripts\python.exe -m pip check
```

PyPI-релиз BlocksNet 0.1.0 требует GeoPandas <1 и несовместим с современными зависимостями проекта. В `requirements.txt` закреплён upstream-коммит `f576517e99c53e74beda29908548f58bfa758e4c`, поддерживающий GeoPandas 1.x; `iduedu==0.4.1` согласован с его контрактом. Установка выполняется обычным pip **с зависимостями**, без `--no-deps`. Требуется Python 3.10–3.12 (установка проверена на 3.11) и доступ к GitHub/PyPI. Старый генератор адаптирован через `src/generation/blocksnet_cutting.py`: используется настоящий низкоуровневый cutter закреплённого пакета без ML-классификатора/torch, с проверками геометрии и метрической CRS. Импорт `main.py` и синтетическая нарезка проверены; полный сетевой конвейер baseline этим не подтверждён. Детали — [ADR 0009](docs/decisions/0009-blocksnet-cutting-bridge.md).

`requirements-audit.lock` фиксирует отдельное минимальное окружение проверок. Не устанавливайте его поверх полного стека: версии NumPy могут различаться; для воспроизведения audit используйте отдельное чистое venv.

### 2. Генерация данных (Запуск вычислений)
Для запуска расчетов (скачивание данных, генерация блоков, AHP и оптимизация) просто выполните:

```bash
python main.py
```
⚠️ `main.py` — старый конвейер с фиксированными путями в `data/processed/`; он не реализует новую политику источников и может перезаписывать результаты. Не запускать поверх ценных данных без изоляции. Время полного расчёта не измерено. Audit-окружение не содержит всех его зависимостей.

### 3. Запуск веб-дашборда
Для визуализации результатов в браузере:
```bash
streamlit run app.py
```
После запуска в терминале появится локальный URL (обычно `http://localhost:8501`), который автоматически откроется в браузере.

## 🛠️ Конфигурация и тюнинг

Главный конфигурационный файл: `configs/ahp_constants.json`.
В нем вы можете редактировать:
- **`scenarios`**: Наборы сценариев (Экоцентризм, Историко-центризм, Инфраструктурный).
- Весовые коэффициенты для каждой связки "Сценарий" -> "Функция (Target Land Use)" -> "Атрибут (Лес, ОКН, Дороги)".
Изменение этих весов меняет только baseline и не создаёт новую модель спроса, прогноз или универсальный сбор данных.
